# FPGA knowledge base release gate

Source: [AMD Embedded local KB deployment](https://github.com/Xilinx/ross-ai-assistant/blob/main/docs/local-kb/README.md) and [operations](https://github.com/Xilinx/ross-ai-assistant/blob/main/docs/local-kb/operate.md).

The AMD package is supplied at `C:\Users\park_cu\Downloads\ross_kb`. The release bundles only `Docker\deb\*` and `MCP\20260918.qwen3-embedding-0.6b.tar.gz` into `kb-runtime.tar.gz`; it intentionally excludes the unused static Docker tarball and standalone Compose binary. The AMD archive contains the CLI, model, image tarballs, snapshot and notices. No AMD runtime or model is downloaded on target PCs.

The FPGA installer uses the user's existing Ubuntu WSL distro and never imports, exports, unregisters or deletes it. It installs Docker Engine and Compose from the bundled DEBs, extracts the AMD archive under `/opt/si-opencode-kb`, runs the AMD CLI, waits for the first snapshot import, and verifies `vivado_doc_search` through Windows localhost. `scripts/build-kb-runtime.ps1 -Output payload/kb-runtime.tar.gz` makes the sidecar. The one-time first import is expected to take time; subsequent starts load the persisted index.

On a clean, disconnected test PC: import the distro for the **installing Windows user**, start it, confirm Docker daemon + Compose and the host's MCP bridge/port, run the search again, reboot, log in and prove automatic startup and another real search. If any step fails, the FPGA installation is incomplete. A reboot requires prior consent. Never unregister an existing unrelated WSL distro. No AMD runtime or model is downloaded during user installation.

## Measured constraints (this repository, 2026-10-21)

The Qwen3-Embedding-0.6B corpus is 725,911 objects at 1024 dimensions. AMD's guide states roughly 8 GB of free disk but says nothing about memory. Empirically on a 15.9 GB Windows host, the WSL default VM size (50 %, about 7.7 GiB) was **not** enough: Weaviate's HNSW load stalled, the MCP server's GraphQL calls failed with `tried to browse non-existing index for <class>`, and WSL itself returned `WSL_SERVICE_TIMED_OUT`. Raising the WSL VM to 12 GB (`memory=12GB`, `swap=8GB` in `%USERPROFILE%\.wslconfig`, then `wsl --shutdown`) stabilised it at roughly 6.8 GB for Weaviate and 1.9 GB for llama.cpp. This is a working setting, **not a verified minimum**, and a successful search has not yet been observed on this machine. Treat the WSL VM budget as roughly 10 GB or more and the host as needing enough RAM to provide it; a 16 GB host has almost no headroom.

Three concrete deviations from the upstream guidance were required:

1. The upstream Windows path is Docker Desktop. Here Docker Engine runs inside WSL2, installed from the offline DEB set in `ross_kb\Docker\deb` (docker-ce, docker-ce-cli, containerd.io, docker-buildx-plugin, docker-compose-plugin plus the Ubuntu iptables/nftables/libnftables/libnftnl/libip4tc2/libip6tc2/libmnl0/libnetfilter-conntrack3/libnfnetlink0 dependencies). `docker-ce` does not configure until those dependencies are present. The `docker` group plus a restart is required before the account can run Docker without `sudo`.
2. `dockerd` must be reachable from Windows, so the unit needs an override (`/etc/systemd/system/docker.service.d/override.conf`) with `ExecStart=` cleared and `ExecStart=/usr/bin/dockerd -H unix:///var/run/docker.sock -H tcp://127.0.0.1:2375`. WSL's localhost forwarding exposes it to Windows; `localhostForwarding=true` and `wsl --shutdown` are required. Binding to `127.0.0.1` only keeps the unauthenticated Docker API off the LAN.
3. The MCP server only stays alive when it is started with `--port 8080 --host 0.0.0.0`, exactly as the AMD-generated compose file does. Started without those flags it exits silently with status 0 after about three seconds. Its `--help` does not list them, so the flags look unsupported but are required. `WEAVIATE_CLASS_NAME` is a `key=value` mapping (`Vivado=<class>`), not a bare class name. The MCP server is correct only once Weaviate has built the vector index for that class; before that it exits with `tried to browse non-existing index`.

The one-time snapshot import is long-running and must not be interrupted: a kill during import leaves a truncated WAL, and Weaviate then rebuilds the HNSW index on the next start, which is far slower and much heavier on memory. The installer must allow a long first-run wait, must not treat "container running" as success, and must confirm a real `vivado_doc_search` result.

A normal WSL or PC restart does **not** rebuild the index. Weaviate loads it from disk (`restore_from_disk` took 233 ms here) and the MCP server became healthy about 18 seconds later; the `restart: always` policy on the mcp service covers the gap while the index is not yet available. The 40-plus minute delay seen here was the one-off rebuild after an interrupted first import, not the normal path.

## Verified end to end on this machine (2026-10-21)

With Docker Engine 29.3.1 and Compose 5.0.2 installed from the offline DEB set inside WSL2, the four AMD images loaded, the Qwen3 snapshot imported 725,911 objects, Weaviate's vector index was rebuilt after the interrupted import, and the MCP server answered from Windows on `http://localhost:8080/mcp/doc-search`. `tools/list` exposed `vivado_doc_search`, and a real query (`Search UG904 for incremental compile.`) returned AMD document chunks with document id, title, `https://docs.amd.com/...` URL and version; a later query returned UG892 "Performing-Implementation-with-Incremental-Compile". The same search also worked after `wsl --shutdown` and a fresh start, and the Rust `--verify-kb` check passed against the running server. The MCP endpoint requires `Accept: application/json, text/event-stream` and a session id from the `initialize` response.

`scripts/build-kb-runtime.ps1` emits the several-gigabyte `kb-runtime.tar.gz` sidecar from the provided AMD files. Keep it next to the installer rather than embedding it in the setup executable, whose practical size limit is about 4 GiB.
